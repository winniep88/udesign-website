# CHIP checkout states

Public checkout stays on WhatsApp while FPX Online Banking and DuitNow QR approval is pending. The public `/api/checkout/status/` returns `available: false` unless all of `CHIP_LIVE_ENABLED=true`, `CHIP_SECRET_KEY`, `CHIP_BRAND_ID`, `CHIP_REFUND_WEBHOOK_PUBLIC_KEY`, and the R2 `BUCKET` binding exist.

For a simulated purchase, the separate `POST /api/test-checkout/` route requires `CHIP_TEST_ENABLED=true`, `CHIP_TEST_SECRET_KEY`, `CHIP_BRAND_ID`, an R2 `BUCKET` binding, and a private random `CHIP_TEST_ACCESS_TOKEN` of at least 32 characters. The request must send that token in `x-udesign-test-token` and originate from the site. There is no customer-facing test payment button. Never use a live key for this route.

The server calculates product and delivery prices, creates a CHIP Purchase, verifies the returned total, Brand ID, and `is_test` flag, and stores the purchase ID and test/live mode with the order. Each Purchase includes `success_callback` pointing to `/api/chip/callback/`. CHIP sends a signed Purchase payload when payment succeeds. The callback checks the raw-body `X-Signature` with the company public key from authenticated `GET /public_key/`, then independently retrieves the Purchase from CHIP and matches its ID, reference, amount, Brand ID, and test/live mode to the stored order before marking it paid. Duplicate callbacks are safe. If the Purchase is still processing, a non-2xx response lets CHIP retry. The return page independently fetches the purchase status; test returns clearly say no real money was collected and no customer order was placed. Simulated purchases have `send_receipt=false`.

The smoke check uses mock CHIP responses and separate RSA key pairs to verify valid, invalid, tampered, and duplicate callback behavior. It also verifies that test credentials cannot enable the public payment button. A real test still requires a CHIP test key and private hosting secrets; the test key is separate from the live key, while the Brand ID is shared. CHIP's available test payment methods can be checked through `GET /payment_methods/?brand_id=...&currency=MYR` using the test key. Do not assume a particular method is available.

For an operator-run simulation, `scripts/chip-test-purchase.mjs` sends a fixed pickup order with dummy contact details to the protected test route. It reads the access token from stdin, returns a CHIP test checkout URL and order ID, and never prints the token. Keep the token and the CHIP test key out of shell history, source files, and customer-facing pages.

Before enabling live checkout: confirm CHIP has approved the intended payment methods; install the live key as a secret; run a low-value end-to-end order and verify the CHIP status, amount, fulfilment, and order record; then explicitly set `CHIP_LIVE_ENABLED=true`. The Purchase success callback records paid orders even when a customer does not return to the site. A merchant-facing order view or notification is still needed before relying on checkout for fulfilment.

For refunds, register a **live CHIP webhook for `payment.refunded`** pointing to `/api/chip/refund-webhook/` and set `CHIP_REFUND_WEBHOOK_PUBLIC_KEY` to that webhook's public key. This key differs from the company public key used for Purchase success callbacks. The webhook verifies the raw signed Payment event, matches its related Purchase back to the stored order, and reads CHIP's current Purchase state. Only a single verified refund Payment whose amount equals the entire order invokes `checkout_record_full_refund`. Partial refunds, including several partial refunds that eventually add up to a full refund, need owner review; the website does not restore a voucher or reverse loyalty points automatically for those cases. If the paid callback was missed, the webhook first records the verified original payment, then its verified full refund. Do not switch on live checkout until this webhook and the owner review workflow are tested.

## Customer accounts and loyalty

The account UI stays unavailable until **all** of `ACCOUNTS_ENABLED=true`, `SUPABASE_EMAIL_READY=true`, `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, and server-only `SUPABASE_SECRET_KEY` are installed. The public `/api/account/config/` returns only the URL and publishable key when enabled. `SUPABASE_EMAIL_READY` must be set only after a verified production email sender is configured for sign-in messages. Store the `sb_secret_` key in hosting secrets; it is used only in the Supabase `apikey` header and never sent to a browser or as an Authorization Bearer token. Browser access tokens are verified against Supabase Auth `/auth/v1/user` before an order is linked to an account. The server checks that the checkout email matches the verified account email. Guests can still check out.

When the Supabase URL and secret are installed, the server also persists guest live orders even if public account signup is still off. It re-prices all cart items, then calls service-only `checkout_prepare_order` to reserve the RM10 welcome voucher or points and persist the order. CHIP receives the verified discounted total via `purchase.total_override`; the returned CHIP total must match the stored order before the checkout URL is shown. A failed Purchase creation releases the reservation. A paid Purchase is verified independently against CHIP before `checkout_mark_paid`; marking an order complete awards points through `checkout_mark_completed`. A signed full-refund Payment event calls `checkout_record_full_refund`, which reverses earned points and restores redeemed points. The browser cannot award or spend points directly. Test mode remains R2-only and cannot create loyalty events. If a signed-in customer starts a new checkout while an earlier one is pending, the server checks CHIP and only frees reserved rewards after CHIP confirms cancellation. CHIP's return link alone does not cancel the purchase.

Private owner order routes are `/api/admin/orders/` and `/api/admin/orders/:id/` (read), `/api/admin/orders/:id/complete/` (award completion points), and `/api/admin/orders/:id/reconcile/` (refresh verified CHIP paid/refund status). For WhatsApp orders, `/api/admin/orders/manual/` records an owner-entered order, while `/api/admin/orders/:id/manual-paid/` and `/api/admin/orders/:id/manual-refunded/` record manually confirmed payment or refund. Those manual endpoints only update the order ledger; they never move money. They require a verified Supabase owner session, a matching server-only `UDESIGN_OWNER_USER_ID`, and an owner row in `admin_members`. There is no website action that initiates a CHIP refund; contact the customer first, refund or replace through the appropriate merchant workflow, then reconcile the result. Owner actions stay closed until the owner account and database membership are provisioned.

The owner-only `GET /api/admin/customers/lookup/?email=...` finds one verified customer account by exact email. It returns `{ "userId": "...", "email": "..." }` on a match and 404 otherwise. It never returns an unverified profile or searches by partial email. Pass the returned `userId` into a manual order to attach it to that customer's account; the database checks the account and email again when the order is created.
